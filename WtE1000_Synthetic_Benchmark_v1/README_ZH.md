# WtE1000-Synthetic v1.0.0 使用说明

本数据包是根据论文已经披露的汇总统计生成的独立合成基准，不包含真实工程
图纸、真实企业名称、原始 BOM 边或原论文中的密码学/区块链运行时间。
需要 Python 3.10 或以上版本，仅使用标准库，无须安装第三方依赖。

## 匹配的规模统计

| 指标 | 合成数据 |
| --- | ---: |
| BOM 节点 | 18,563 |
| 叶级数据实体 | 4,116 |
| 最大层数 | 19 |
| 工程专业类别 | 9 |
| 合成 SPC 身份 | 52 |
| 图纸页清单 | 12,820 |
| 逻辑文件负载 | 272,000,000,000 字节，即十进制 272 GB |
| 合成文件最小值 | 4,096 字节 |
| 文件最大值 | 280,000,000 字节，即十进制 280 MB |

原文的“约”数值在合成集内作为精确目标使用。GB=10^9 字节、MB=10^6 字节，
是本基准明确采用的单位约定，不代表恢复了真实项目的精确字节数。
根节点记为第 1 层，因此 19 层对应最长路径 18 条边。
原文“数 KB”的下界在此选择为 4,096 字节，属于公开的合成假设。

## 直接验证和复现

解压后，进入本目录运行：

    python validate.py --data data
    python reproduce.py --data data
    python benchmark.py --data data --repeats 5 --output traversal_results.json

validate.py 独立核对节点、边、层数、叶节点、企业映射、文件大小及工作负载。
reproduce.py 在临时目录重新生成全部元数据，检查逐字节一致性，并验证校验器能
识别人为注入的文件大小错误、图环和无效企业编号。
benchmark.py 只测量从已给定受影响根节点向下遍历并去重 SPC 的参考实现；
它不运行 ABE、变色龙哈希、秘密重构、区块链或网络通信，因此不能代替原论文的
Init、Enc、Dec、Co-Editing 测量。

从配置重新生成同一份数据：

    python generate.py --config config.json --output regenerated_data
    python validate.py --data regenerated_data

更换随机种子，并取消共享引用，进行消融测试：

    python generate.py --seed 42 --shared-leaves 0 --output alternate_data
    python validate.py --data alternate_data

输出目录必须不存在或为空。固定种子使用明确实现的整数伪随机算法；元数据采用
UTF-8 和固定换行格式，不依赖 Python random 模块的采样实现。

## 主要文件

- nodes.csv：BOM 节点、层数、FP/MW/CP 类型、专业、实体和责任方。
- edges.csv：基础树结构及共享叶节点的额外引用边。
- entities.csv：4,116 个叶实体的归属、图纸页数和字节总量。
- pages.csv：12,820 个文件的精确逻辑长度、公开生成种子和相对路径。
- spcs.csv、disciplines.csv：合成企业编号与专业标签。
- modifications.jsonl：1,000 条合成修改任务及预期影响范围。
- confirmation_batches.jsonl：1、2、5、10、20、52 方确认测试的参与方集合。
- generation_config.json：完整配置；summary.json：生成后统计。
- manifest.json：元数据文件的 SHA-256 校验清单。
- reports 目录：独立校验、固定种子复现及参考遍历的实际测试报告。

所有节点/企业编号均为虚构标识。52 家协作企业在这里建模为 52 个 SPC 身份；
LC 另作为一个逻辑协调角色，不列入 spcs.csv。这是明确的合成建模约定。

## 合成假设与局部修改场景

基础树有 18,562 条边，默认再加入 412 条共享叶节点引用边。412 不是原项目观测值，
而是可配置的合成参数。所有边均连接相邻层，保证有向无环和最大层数。

局部任务采用作者给出的“最多 6 层、282 个节点”作为场景上限。为覆盖边界，专门
构造了一个 6 层、282 个节点的子图，各层节点数为 [1,5,20,56,90,110]。
该具体形状完全由程序合成，不是真实 BOM 的提取结果。
其他任务对满足上限的子图进行偏向较大范围的随机抽样，不模拟真实修改发生频率。

每条任务明确给出 affected_roots，参考实现从这些根节点向下遍历并去重叶节点责任方。
“哪些祖先实际受影响、何时停止向上传播”仍是场景输入，未假装由随机数据恢复真实
制造业务语义。需要评估自己的工程传播规则时，可在同一图上接入自己的选择算法。

确认微基准的参与方集合与 BOM 局部修改任务分开保存。t 方确认对应 t 笔确认交易、
t+2 笔账本写入及 t 次独立确认查询；数据包没有编造提交延迟或 TPS。

## 按需生成 272 GB 文件负载

压缩包只包含轻量元数据和生成器。272 GB 是文件清单对应的逻辑负载总量，
不等于压缩包已经携带 272 GB 文件。生成的是确定性的二进制测试内容，不是 CAD 图纸。

仅查看前三个文件前缀的生成计划，不写入文件：

    python materialize.py --data data --mode prefix

生成第一个完整文件，其大小为 4,096 字节：

    python materialize.py --data data --mode full --page-id P000001 --execute

只生成最大逻辑文件的前 16 KiB：

    python materialize.py --data data --mode prefix --page-id P000002 --prefix-bytes 16384 --execute

需要完整负载时，生成全部文件：

    python materialize.py --data data --mode full --all-pages --execute

完整模式会实际写入 272 GB 负载及额外文件系统开销。生成器按 1 MiB 分块写入，
不会一次把整个文件放进内存。已有文件不会被覆盖。

还提供 sparse 模式用于元数据或文件系统功能测试；稀疏文件包含零填充空洞，
不能拿它的磁盘占用、压缩率或读写结果冒充完整负载的性能。
prefix 模式同样不能冒充完整文件，输出报告会记录逻辑大小和实际生成大小。

## 可以如何用于论文

可以说明“提供了匹配公开规模统计的独立合成基准及固定种子生成器”。
不能说明“公开了原始工业数据”“提炼并复现了真实分支/共享比例”，也不能把本包的
参考遍历时间当作原论文的系统运行时间。全协议性能仍需接入自己的密码学和区块链实现。
